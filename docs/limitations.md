# Scope and evidence

The reference profile simulates a single Franka workcell in Isaac Sim 6.2 on Windows. Each episode has zero or one configured fault. The fault models operate on virtual signals, command paths or position targets. Their physical effect is measured within the simulated scene.

The mock backend tests phase order, queue behavior, reset, serialization and verdicts. Hardware-dependent claims require a run from the Windows Isaac profile and its actual environment, asset and protocol locks. The same evidence can be replayed from WSL2 without Kit.

The campaign contains two fixed workcells and a finite set of blocked initial states. Rankings or rates apply to that protocol and candidate. A software release report records expected thresholds, infrastructure failures, incomplete obligations and any optional study components that were not performed.

The primary evaluation includes all 820 registered rows. Seed 1000 had been observed during development and contributes 68 rows. Seeds 1001–1019 contribute 752 rows. Conditions and repeat indices can share the same physical starting state. Mutants were scheduled only on seeds 1000–1004, so the two seed groups have different mixes of reference and mutant trials. Comparisons across the two groups should match the cell, controller and fault condition. [Commissioning history](adr/002-gripper-commissioning.md)

Cell A's two gripper-signal conditions each produced 40 reference stop-time violations. The stop commands took effect at the recorded abort boundary. The fingers then exceeded their 0.003 m/s limit during the required dwell. Across all 80 attempts, the first uninterrupted dwell finished 26 steps (216.7 ms) after the deadline. These traces identify the limiting joint speeds. Establishing which physical or control parameter caused the residual motion would require a separate experiment. [Physical settling after abort](../results/publication/candidate-8ad96bd/primary/r06-physical-diagnosis.md)

Cell B's F4 clamp-command delay took effect in 40 of 50 activated trials (80%, against a 98% target). A retrospective audit of the sealed command and event streams found that all 40 reference controllers issued the close command three steps after the trigger. The 10 M4 controllers entered the close stage, but none issued a clamp-close command anywhere in the episode. These 10 remain in the planned denominator as `NOT_EXERCISED`. Moving the trigger on those recorded paths would yield no close command to delay. [Registered mutant pairs](../results/publication/candidate-8ad96bd/tables/paired_mutants.csv) · [Full-episode command audit](../results/publication/softwarex-extension/cell-b-f4-opportunities.json)

In the canonical campaign, 60 simulated seconds took a median of 38.37 s in Cell A and 45.28 s in Cell B during the measured running phase. The foreground CellIO work in a four-step interval had a 99th percentile of 10.57 ms and 11.70 ms, respectively, above the recommended 3.33 ms. Users budgeting controller time should allow for this cost. The aggregate timer includes event and signal handling, fault and command processing, oracle evaluation and record preparation. Separate component measurements would be needed to identify the largest contributor before optimizing it. [Canonical timing by cell](../results/publication/candidate-8ad96bd/tables/performance.csv)

In the persistent-worker test, 200 measured episodes ran after ten warmups. Comparing the first and last 20 measured episodes, the process working-set median rose from 4,987.4 to 5,366.9 MiB, an increase of 379.5 MiB against a 256 MiB alert threshold. GPU memory attributed to the worker rose by 212 MiB. The worker alternated between cells on every episode. These end-of-episode measurements show growth across repeated reloads and leave its cause open. A follow-up can compare fixed-cell runs with alternating-cell runs and record live allocation counts and memory reserved by the allocator before and after each reload.
